# AGENTS.md — aimedia

Краткий маршрут для coding-агентов. Общение, планы и отчёты — по-русски.
Подробные устойчивые правила хранятся в корневой папке `instructions/` и здесь
не дублируются.

## Начало работы и источники истины

1. Прочитай [карту проекта и план реализации](docs/plans/README.md), затем документы
   `docs/plans/01-product-scope.md`–`09-documentation-help.md`, относящиеся к задаче.
2. До первой записи проверь фактическое дерево, Git branch/worktree, status и чужие
   изменения. План, пример, fixture или mock не выдавай за реализованную функцию.
3. Документы `01`–`09` задают исходные продуктовые и архитектурные контракты;
   `docs/plans/README.md` связывает их в этапы E00–E11 и содержит предлагаемые
   уточнения. Предложение из README не исправляет противоречие в исходной
   спецификации автоматически.
4. После E00 принятые `release-scope.md`, `decisions/implementation-baseline.md` и
   `verification-matrix.md` становятся источниками решений по развилкам. До их
   появления не закрепляй спорную трактовку молча: зафиксируй блокер или change note.
5. Код, manifests, тесты и evidence после их появления отражают фактическое
   состояние реализации. `NOT_RUN`, `SKIPPED`, `XFAILED` и `NOT_COLLECTED` не равны
   `PASSED`; локальный commit не равен принятому этапу или релизу.

## Инструкции: читать и поддерживать

Перед изменениями прочитай **все** инструкции, относящиеся к затронутой области.

| Инструкция | Когда читать |
|---|---|
| [DOCS.instructions_style](instructions/DOCS.instructions_style.instructions.md) | Создание, обновление, переименование, разделение или удаление инструкций и `AGENTS.md` |
| [DOCS.commit_messages](instructions/DOCS.commit_messages.instructions.md) | Подготовка staging, проверок и локального Git commit |
| [CORE.code_intelligence](instructions/CORE.code_intelligence.instructions.md) | Поиск реализации, символов, связей, структурных паттернов и оценка влияния |

- **Каждую новую инструкцию обязательно добавляй сюда** рабочей Markdown-ссылкой
  и точным условием чтения. При переименовании, разделении или удалении обновляй
  каталог и все затронутые маршруты.
- **Если в том же логическом изменении меняется устойчивый owner, контракт,
  workflow, команда проверки, правило данных, ограничение безопасности или другой
  важный инвариант, обнови соответствующую инструкцию по
  `DOCS.instructions_style`.** Если владельца ещё нет — создай отдельную инструкцию
  и добавь её в каталог. Не откладывай это до будущей задачи.
- Не создавай инструкцию для временного статуса, разового эксперимента или истории
  инцидента. Не дублируй большие фрагменты планов и соседних инструкций.
- Держи `AGENTS.md` кратким навигатором: подробные команды, матрицы и правила
  подсистем выноси тематическому владельцу в `instructions/`.

## Работа с кодом

Используй **Codebase Memory, Serena и ast-grep по назначению** согласно
`CORE.code_intelligence`: Codebase Memory — владельцы, архитектура и связи; Serena —
символы, декларации и references; ast-grep — синтаксические структурные паттерны.
Перед чтением целого source-файла начни с Serena; перед изменением поведения,
интерфейса или имени проверь references. Критичные результаты индекса сверяй с
актуальным worktree. Для известных документов и manifests используй прямое чтение;
runtime-поведение доказывают тесты и безопасные trace/logs, а не статический граф.
Недоступность инструмента отмечай явно и используй узкий fallback.

## Ключевые границы v0.1.0

- Целевой стек: Python 3.12+, uv, Typer/Rich, httpx/asyncio, Pydantic,
  Peewee/SQLite, Pillow, YAML и platformdirs; версии подтверждаются lockfile и CI.
- Первый релиз — image CLI через Polza. STT/TTS, текстовые генерации, embeddings,
  sqlite-vec, видео, GUI, MCP, сервер и брокер очередей не входят в v0.1.0.
- `Job` — один запуск; retry создаёт новый Job; sync/recovery продолжает известное
  remote execution и не делает скрытый повторный submit; `Artifact` — сохранённый
  и проверенный локальный результат.
- Деньги хранятся точно через Decimal; разные валюты, неизвестная цена и ноль не
  смешиваются. Наличие YAML-записи не доказывает живую поддержку модели.
- Секреты не передаются через CLI, URL, fixtures, логи, БД или evidence. Offline
  tests не используют внешнюю сеть и пользовательский data-root; live-вызовы только
  по явному разрешению и с ограниченным планом расходов.
- Не расширяй release scope, не активируй непроверенную модель и не ослабляй
  recovery/security-инвариант ради зелёного теста без принятого решения E00/ADR.

## Исполнение, Git и отчёт

Работай небольшими срезами: контракт → тест/проверяемое утверждение → реализация →
negative/failure cases → документация и инструкция → проверки → review → commit.
Не включай чужие изменения или несвязанный рефакторинг. Сохраняй raw exit code
каждой обязательной проверки; успешный последний элемент pipeline не маскирует
предыдущий failure.

Делегирование — только при разрешении пользователя или применимых инструкций; один
writer на checkout/worktree, reviewer — read-only, staging и commits — у основного
интегратора. Push, публикация, tag/release и опасные Git-операции требуют отдельного
явного разрешения по инструкции коммитов.

В финальном отчёте перечисли изменённые пути, фактические проверки и их результаты,
пропуски/блокеры и следующий шаг. SHA сообщай только после реально созданного commit.
