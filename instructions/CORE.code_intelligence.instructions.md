# CORE — Codebase Memory, Serena и ast-grep

## Правило выбора

При работе с кодом используй Codebase Memory, Serena и ast-grep по назначению, а не
заменяй исследование последовательным чтением больших файлов через grep/read.
Запускай инструмент по вопросу, не все три ради формального отчёта. Документы,
известные manifests, состояние файловой системы и запуск проверок требуют прямого
чтения или shell, а не символьного поиска. Пока исходников нет, code intelligence
не заменяет спецификации и не может подтвердить реализацию.

| Вопрос | Инструмент и первый шаг |
|---|---|
| Где реализовано неизвестное поведение, кто владелец? | Codebase Memory: `search_graph` с небольшим limit; `search_and_read_symbols`, если нужен исходный код |
| Как связаны владельцы или проходит workflow? | Codebase Memory: direct neighbors для одного перехода, `trace_path` глубиной 2–3 для нескольких |
| Известны имя символа или source-файл | Serena: `serena_find_symbol` либо `serena_get_symbols_overview` до чтения целого файла |
| Что затронет изменение интерфейса/поведения/имени? | Serena: `serena_find_referencing_symbols`; Codebase Memory: `detect_changes` для существующего diff |
| Найти похожую конструкцию или форму вызова | ast-grep: `ast_search` с конкретным паттерном, языком и узким путём |
| Найти точную строку, env key, route или message | Codebase Memory: `search_code`; прямой read/rg для подтверждения |
| Прочитать известный README, план, YAML или manifest | Прямое чтение файла |
| Доказать выполнение, retry, race или порядок событий | Test, безопасные logs/trace и воспроизведение; статического графа недостаточно |

## Последовательность исследования

1. Для концептуального вопроса найди вероятного владельца через Codebase Memory. Для
   известного символа или файла начинай сразу с Serena.
2. Проследи только нужные связи; ограничивай выдачу и глубину. Несколько известных
   символов читай пакетно вместо repository dump.
3. Уточни declaration, body и references через Serena. Перед изменением публичного
   интерфейса найди реализации и callers; не предполагай единственный call site.
4. Для повторяющейся синтаксической формы используй ast-grep. Сначала проверь
   pattern на известном положительном примере, затем расширяй scope. AST-match —
   кандидат для анализа, не доказанная ошибка.
5. Подтверди критичные строки непосредственным чтением актуального worktree,
   отредактируй минимальный участок и проверь поведение тестом.

Если graph/snippet сокращён, сначала повтори запрос с подходящим лимитом или
`full_output`, а не считай обрезанный фрагмент полным контрактом. Отсутствие
совпадений не доказывает отсутствие функции: проверь имя, область, язык и
актуальность индекса.

## Worktree, ограничения и fallback

- Убедись, что индекс относится к нужному checkout. Для Serena в worktree указывай
  точный project path; не перенастраивай общий проект без необходимости.
- Не выдавай индекс другой ветки или старого состояния за текущий dirty worktree.
  Критичный путь и тело подтверждай на диске; stale index отмечай как ограничение.
- Если backend недоступен, зафиксируй это и используй узкий read/rg fallback. Не
  устанавливай и не перенастраивай общие сервисы без разрешения.
- Поиск не разрешает массовый AST rewrite или rename. Для изменения нужны scope,
  references, preview/diff и проверки; auto-fix всего дерева вслепую запрещён.
- Статический граф не доказывает network outcome, порядок coroutine, ownership
  ресурсов, отсутствие races, точность денег или безопасность данных.

Инструменты ускоряют навигацию, но не расширяют полномочия агента и не заменяют
release gates R01–R24.
